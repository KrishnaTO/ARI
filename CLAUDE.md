# CLAUDE.md

Guidance for Claude Code when working in this repository (`KrishnaTO/ARI`).

## What belongs here

**If a curator's decision changes it, it belongs here. If a code change changes it, it belongs to
the app** — [`KrishnaTO/ARI-metadata-manager`](https://github.com/KrishnaTO/ARI-metadata-manager),
which is the editor at <https://aurint.ca/ari-editor/>.

This repository is the record: the ontology, the curated mapping set, the master lists and the
generated reports. It holds **no application code**. The app reads the ontology and mappings from
here and opens pull requests back into here under each curator's own GitHub identity.

| Belongs here | Belongs in the app repo |
| --- | --- |
| `ontologies/*.owl` — the sole authority: `ari_disease.owl` is the disease record, with `ari_core`, `ari_symptoms`, `ari_anatomy`, `ari_biomarkers` and the generated `ari_symp` / `ari_uberon` / `ari_pr` / `ari_chebi` / `ari_hgnc` / `ari_loinc` slices | `app/`, `static/`, `deploy/`, `tests/` |
| `mappings/*.tsv` — every curated judgment | `data/2-databases/*.tsv` — reference indexes built from public releases |
| `data/1-master`, `3-meta-database-sources`, `4-reports` | `mappings/ari.predicted.sssom.tsv` — a machine export nothing here consumes |
| `notebook/`, `sparql/`, `data_model/` | Anything a code change, not a curator, would alter |

A file that is regenerated by running a script, with no human judgment anywhere in the path, is a
build product and belongs with the code that builds it — even when it is tabular.

## Development workflow

### 1. Work in worktrees
- Do **not** work directly on `main` or in the primary checkout. Create a dedicated git worktree per
  task and work there: `git worktree add .claude/worktrees/<slug> -b <branch> origin/main`.
- Branch naming: `issue-<n>/<slug>` when the work resolves a GitHub issue, otherwise a short
  descriptive slug. Curator edits published by the app use `edit/<login>/<topic>-<timestamp>` and
  are created by the app, not by hand.

### 2. Commit, push, and open PRs
- Commit when the work is complete, push to `origin`, and open a pull request against `main`.
- Use the `gh` CLI. Reference the issue the work resolves with `Closes #<n>` in the PR body.
- Don't push work-in-progress unprompted.

### 3. Check the other worktrees first
- `git worktree list`, then `git -C <path> status` and `git -C <path> log --oneline origin/main..HEAD`
  for anything related, so effort isn't duplicated or overwritten.

### 4. Record the change
- Add an entry to [changelog.md](changelog.md) under a `## <branch-name>` heading, saying what
  changed and **why**. Existing entries are the style guide.

## Repository notes
- **`main` is the only long-lived branch.** The app is developed in its own repository; there is no
  app branch here. (`feature/metadata-manager_v2/ARI` was retired — see
  `archive/metadata-manager-v2` if you need its history.)
- [`.github/scripts/validate_mappings.py`](.github/scripts/validate_mappings.py) validates the
  mapping files against each other and against the ontology. It needs only the standard library:
  `python .github/scripts/validate_mappings.py`, or `--since main` for only what a branch changed.
  `Validate mappings` gates pull requests; `Audit mappings` sweeps everything on Mondays.
- **Every `ontologies/*.owl` is in one canonical layout**, written by `tools/format-owl.sh` (ROBOT,
  pinned in `tools/robot.version`); the `OWL format` workflow rejects a file that is not. Read and
  edit the ontology as XML, never by line or regex, and run the formatter (or commit through
  `.githooks/pre-commit`) after any write. In this checkout Java 11+ is in WSL, not Windows:
  `wsl -e tools/format-owl.sh <file>`. Format through `ontologies/catalog-v001.xml` (it resolves the
  imports), and declare a property only in `ari_core.owl`.
- The SSSOM header is shared with the app's writer. `SSSOM_COLUMNS` here and `SSSOM_COLS` in the
  app's `app/sssom_service.py` must agree, or every curator publish fails the header check.
- Prefer the curated master list as the source of truth. Keep changes surgical and on one data path
  at a time.
- Use local ontology and report artifacts rather than online sources when generating matching output.
- **Do not read `.env` files** unless explicitly authorized.
- `data/2-databases/` is untracked local scratch for large raw release dumps — nothing in it is
  version-controlled here.
